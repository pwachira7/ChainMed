# ChainMed

Blockchain-Based Secure Audit Logging and Access Control for Care Operations Management.

ChainMed connects fictional emergency reporting, care staff coordination, transactional audit capture, Ethereum commitments, integrity verification and investigation feedback. PostgreSQL stores operations and evidence; the chain stores only opaque event UUIDs and SHA-256 commitments.

## Run locally

Use **Node.js 22 LTS** (`nvm use`), npm, and either Docker Compose or the bundled development PostgreSQL launcher. Node 25 was available during development and generated a Hardhat support warning; use Node 22 for reproducible installations.

```sh
npm ci
npm run setup:env
npm run db:generate
```

`setup:env` creates a private, gitignored `.env` with random development secrets. Review it locally. Keep `DATABASE_URL` and `POSTGRES_PASSWORD` consistent when changing either. Do not commit this file.

Start PostgreSQL in its own terminal:

```sh
# Option A: Docker
 docker compose up -d postgres
# Option B: development-only, native PostgreSQL bundled by npm
 npm run db:local
```

Then migrate and seed:

```sh
npm run db:migrate
npm run db:seed
```

Start the local chain in another terminal:

```sh
npm run chain
```

Deploy and configure its disposable signer:

```sh
npm run deploy
node scripts/configure-local-chain.mjs
```

`configure-local-chain.mjs` works only with development mode and chain 31337. It loads Hardhat's publicly known local development signer into `.env`. Never fund this signer or use it on a public network. For another network, configure `CONTRACT_ADDRESS`, `CHAIN_ID`, `RPC_URL` and a separately authorized `BLOCKCHAIN_PRIVATE_KEY` manually.

Start the applications and the worker in separate terminals:

```sh
npm run dev
npm run worker
```

Open [ChainMed](http://localhost:5173). API: [health](http://localhost:4000/api/health), [Swagger UI](http://localhost:4000/api/docs). Use **localhost**, matching `WEB_ORIGIN`. The worker anchors events every five seconds and reconciles the complete inventory every five minutes. Reload views to see background changes. Pending anchoring is a real queue state, not a simulated success.

## Validation

With PostgreSQL, the local chain, API, frontend and worker running:

```sh
npm run typecheck
npm run build
npm run test:contract
npm test
npx playwright install chromium
npm run test:e2e
npm run measure
```

Tests use a fresh `chainmed_test_*` PostgreSQL schema per run and deploy a separate registry. Each run creates isolated fictional identities. Contract compilation must have run before `npm test` (the contract test command does this). API tests exercise actual PostgreSQL transactions and local Ethereum, not mocked persistence. Browser tests run sequentially and share a fictional incident across roles. Do not run integration and performance suites concurrently because both use the test inventory. On a repeated browser run, the newest matching report is used.

Reports in `docs/testing/` are generated by actual executions. `docs/screenshots/` contains actual browser screenshots. Performance measurements describe this local environment only. See [testing methodology](docs/testing/README.md).

## Demonstrate the research contribution

Follow [the demonstration guide](docs/DEMO.md): submit as citizen; review and assign as admin; update as staff; verify as auditor; modify/delete an isolated demo fixture with a development-only CLI; reconcile the full inventory; investigate the resulting notification. There is no audit update/delete API.

## Architecture and scope

- `frontend/`: React 19, TypeScript, Vite, Tailwind, accessible forms and responsive role-aware navigation.
- `backend/`: Express, Zod, Prisma 6, JWT sessions, bcrypt, audit service, durable anchoring worker, verification and reports.
- `backend/prisma/`: normalized PostgreSQL schema, committed migration and development seed.
- `blockchain/`: Solidity `ChainMedAuditRegistry`, Hardhat deployment and authorization tests.
- `tests/`: unit, PostgreSQL/API/blockchain integration, browser and performance checks.
- `docs/`: requirements, schema, API reference, diagrams, security assumptions and dissertation support.

The centralized permission matrix lives in `backend/src/services/permissions.ts`. Every protected endpoint authenticates against an active database session and current user role. Refresh tokens are random, hashed in PostgreSQL, rotated, and delivered in HTTP-only SameSite Strict cookies. Access tokens stay in browser memory. Cookie operations require an exact trusted Origin. Operational writes and audit+outbox inserts share a transaction. Audit chain-head selection and worker signer use PostgreSQL advisory locks. Incident updates require the current version, preventing lost updates; creation requires a per-user idempotency UUID.

### Material limitations

This is a capstone system for fictional demonstrations, not a certified emergency dispatch or clinical platform. A local single-node chain cannot provide the trust properties of an independently administered decentralized network. A compromised signer can anchor false new evidence; a database owner can change application records. The integrity engine detects divergence from existing chain commitments, not whether the original report was truthful. Deployment keys and registry address must be retained for evidence continuity. See [threat model](docs/security/THREAT_MODEL.md).

Production password reset delivery deliberately returns 503 until an external delivery service is integrated; development exposes reset tokens for local demonstration only. There is no outbound email integration. API binds to loopback; production needs a TLS reverse proxy, least-privilege database credentials, backups, external chain governance, shared rate limiting and operational monitoring. Full-inventory verification is sequential and the UI shows the latest 100 verification runs; large deployments need indexed per-event results and chunked jobs. Exports are redacted and limited to 5000 filtered records.

## Troubleshooting and reset

- Prisma cannot find an engine: rerun `npm run db:generate` with network access. On constrained hosts, use `XDG_CACHE_HOME=/tmp/chainmed-cache`.
- Connection refused: start PostgreSQL and Hardhat before migrating, deploying or testing.
- Refresh returns 403: use the URL in `WEB_ORIGIN`, including its port; restart the API after changing `.env`.
- Pending/failed anchors: start the worker, check authorized signer, contract address, RPC and chain ID. Queue entries retry with capped exponential backoff; they are retained on errors.
- Blockchain restart: Hardhat state is ephemeral. A new chain loses old commitments. For a clean demonstration reset, stop all services, create a fresh database name in `.env` (or explicitly reset the dedicated disposable Docker volume), start the database, migrate, seed, restart Hardhat, deploy, configure, and restart API/worker. Never reset a database holding evidence you need to preserve.
- The native PostgreSQL launcher stores data in gitignored `.local/postgres`; stop it with Ctrl+C. Docker data is in a named volume.
